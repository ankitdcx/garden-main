# WP-007 — Garden-governed evolution pipeline

Status: IN PROGRESS — STEP 1

## Objective

Treat the pipeline that reviews, implements, and evolves Garden as a Garden application rather than as adjacent automation. Existing Garden/GSL mechanisms govern the pipeline: typed ACTION semantics, DesignEpoch, bounded authority, ActionGate, immutable predecessor releases, and human canonical-promotion authority.

## Existing canonical obligation basis

This work package is a DERIVATION from existing v15.5 mechanisms, not a new top-level architecture proposal.

- `canonical/current/Garden_System_v15.5_FULL_2026-09-12.txt` already specifies an agent proposal path through capability lookup, principal/delegation checks, deterministic ActionGate, safety/assurance gates where applicable, dispatch, and effect receipt/reconciliation.
- The same canonical System source already requires governed DesignEpoch transitions for authoritative semantic change and binds candidate generation/materialization to source hashes and DesignEpoch.
- Published v15.5 remains immutable. Successor materialization is governed separately by WP-006 and does not itself imply canonical promotion.

## Correctness order

1. **Type verbs** — PROPOSE, TRIAGE, TEST, ACCUMULATE, MATERIALIZE; explicit pre/post conditions.
2. **Epoch bind** — every finding, test, and delta binds to DesignEpoch; stale artifacts cannot accumulate without re-derivation.
3. **Envelope agents** — reviewers, test writers, and integrators receive only bounded role authority; no self-minting, delegation expansion, or canonical-promotion authority.
4. **Gate actions** — every evolution action passes ActionGate; rejected/escalated actions receive receipts.
5. **Config as delta** — schedules, prompts, role registries, and pipeline policy become governed configuration-delta objects.
6. **Constitutional tier** — changes to gate/envelope/epoch-binding rules require the higher human approval path.
7. **Level-2 falsifiability** — attack Garden's governance of its own evolution (gate bypass, authority expansion, stale-epoch accumulation, unauthorized promotion).

## Throughput hold

Do **not** add parallel dispatch, a new integrator-challenger, or a findings ledger before Steps 1–4 are implemented and tested. More activity before typed/gated transitions would scale churn rather than correctness.

## Step 1 boundary

`implementation/garden_kernel/evolution_actions.py` defines exactly five pipeline verbs as a bounded application/profile over existing GSL ACTION semantics. Each verb has explicit preconditions and postconditions. Step 1 deliberately does **not** evaluate DesignEpoch freshness, authority envelopes, or ActionGate policy; those are Steps 2–4.

Materialization means creation of a complete successor **candidate** only. Its contract requires predecessor and canonical pointer to remain unchanged. Human canonical promotion is intentionally outside these five agent pipeline verbs.

## Failure guards

- **Repo ahead of design:** no implementation delta may be admitted without a source obligation/provenance link.
- **Activity without progress:** measurement/ledger work is deferred until the correctness core (Steps 1–4) exists.
- **Reflexive authority growth:** no agent may create or enlarge its own authority.
- **Stale design state:** Step 2 must make stale epoch bindings fail closed for accumulation/materialization.
